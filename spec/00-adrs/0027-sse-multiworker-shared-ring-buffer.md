# ADR-0027 — SSE Multi-Worker Shared Ring Buffer (SQLite WAL-Backed)

> **Status:** Accepted
> **Date:** 2026-04-28
> **Supersedes:** —
> **Superseded by:** —
> **Related:** ADR-0002 (WordPress plugin runtime), ADR-0025 (SSE realtime transport), ADR-0021 (no localStorage), ADR-0026 (LWW canonical tie-break)
> **Closes:** AUDIT-06 (MED) · P77 · ADR-0025 §Negative bullet 3

---

## 1. Context

ADR-0025 mandates Server-Sent Events as the **sole** realtime transport for WorkFlowy and specifies a **5-minute ring buffer** keyed by `ServerSeq` so reconnecting clients can replay missed frames via the standard `Last-Event-ID` header.

ADR-0025 §Negative explicitly flagged a follow-up:

> "5-minute ring buffer is in-memory per worker pool → multi-worker deployments need a shared store (Redis/SQLite WAL); flagged as a follow-up rather than blocker."

In production WordPress hosting, **PHP-FPM almost always runs ≥2 worker pools** (default `pm.max_children` ≥ 5) for request concurrency. A purely per-process ring buffer therefore breaks the `Last-Event-ID` replay contract:

- Client reconnects, lands on a **different worker**, asks for `Last-Event-ID: 4711`
- New worker has its own ring starting at `ServerSeq = 5023` — gap is invisible
- Client receives `5024+` and **silently misses** events `4712..5022`

Silent gaps violate the LWW resolution model (ADR-0026) because the local mirror never learns about the upstream writes and will re-send stale state on the next action, producing **client-induced data regressions**.

Redis is forbidden by the resolved backend stack (memory: "Backend RESOLVED 2026-04-25: WordPress plugin (PHP 8.1+ + SQLite + REST). Lovable Cloud, Supabase, sql.js, IndexedDB-as-primary, Postgres, MySQL, standalone Node, Cloudflare D1, Go all forbidden."). The shared store **must** be SQLite.

---

## 2. Decision

Adopt a **SQLite WAL-backed ring buffer table** (`SseRing`) as the single shared event log across all PHP-FPM workers. The buffer is durable, lock-free for readers (WAL mode), and bounded by a TTL-based reaper.

### D1 — Shared table schema (canonical DDL)

```sql
CREATE TABLE IF NOT EXISTS SseRing (
  ServerSeq      INTEGER PRIMARY KEY AUTOINCREMENT,
  Channel        TEXT    NOT NULL,           -- "page:{ItemId}" | "user:{OwnerId}"
  EventType      TEXT    NOT NULL,           -- e.g. "ItemUpserted", "ItemDeleted", "Heartbeat"
  PayloadJson    TEXT    NOT NULL,           -- PascalCase wire frame body, validated against envelope
  CreatedAtUnix  INTEGER NOT NULL,           -- epoch seconds, UTC
  CreatedAtNano  INTEGER NOT NULL DEFAULT 0  -- monotonic tiebreak within same second
) STRICT;

CREATE INDEX IF NOT EXISTS Ix_SseRing_Channel_Seq
  ON SseRing(Channel, ServerSeq);
CREATE INDEX IF NOT EXISTS Ix_SseRing_CreatedAtUnix
  ON SseRing(CreatedAtUnix);
```

Naming follows ADR-0014 PascalCase DDL rules; `STRICT` mode is mandatory (ADR-0008).

### D2 — WAL mode is mandatory

The plugin MUST set `PRAGMA journal_mode = WAL;` on the realtime DB connection at boot. WAL gives single-writer / many-reader concurrency without blocking the FPM workers serving the SSE long-polls.

### D3 — Producer contract (write path)

Any REST `action` handler that mutates state MUST, **inside the same transaction** that writes to `Items`/`Mirrors`/etc., also `INSERT INTO SseRing(...)` one row per channel that should observe the change. The transaction is the **sole egress** to realtime — a producer that forgets to write the ring frame is a `G-27-PRODUCER-COMPLETENESS` violation.

`ServerSeq` is generated by `AUTOINCREMENT` and returned to the action's REST envelope under `Attributes.ServerSeq` so the writer's own SSE stream can dedupe (`MUST NOT re-apply own writes` per ADR-0023 D6).

### D4 — Consumer contract (SSE stream worker)

The `/stream/page/{id}` and `/stream/user/{id}` endpoints (ADR-0025) MUST:

1. On connect, parse `Last-Event-ID` (default `0`).
2. `SELECT * FROM SseRing WHERE Channel = ? AND ServerSeq > ? ORDER BY ServerSeq ASC` — replay the gap synchronously **before** entering the live loop.
3. Then poll the ring at a **500 ms cadence** for new rows (`ServerSeq > LastSentSeq`).
4. Emit each row as an SSE frame with `id: {ServerSeq}\n` so the client can reconnect on the same offset.
5. Send a `Heartbeat` frame every 15 s (ADR-0025 D6) — the heartbeat is **not** persisted to `SseRing` (ephemeral keep-alive only).

### D5 — TTL reaper (single shared cleanup job)

A WP-Cron job `workflowy_reap_sse_ring` runs **every 60 seconds** and executes:

```sql
DELETE FROM SseRing
 WHERE CreatedAtUnix < (strftime('%s','now') - 300);
```

Five-minute retention matches ADR-0025's stated buffer window. The reaper is **idempotent** and safe to run from any worker — WAL handles concurrent reads during the delete.

### D6 — Cold-gap → `resync` frame

If a consumer's requested `Last-Event-ID` is **older than the oldest row** in `SseRing` (i.e. the client was offline > 5 minutes), the stream MUST emit a single frame:

```
event: resync
id: {currentMaxSeq}
data: {"Status":"Pending","Attributes":{"Reason":"ColdGap"}}
```

…and then end the stream. The client treats `resync` exactly as a fresh page load (full loader fetch via ADR-0023 D1). This matches the existing ADR-0025 §D7 cold-gap contract.

### D7 — Fan-out is N×1, never 1×N

Producers write **one** row per (Channel, event). Consumers each tail their own filtered cursor. No worker holds a list of "subscribed clients"; there is no in-process pub/sub. This makes the system **stateless across PHP-FPM processes** — any worker can serve any reconnect, the property AUDIT-06 demanded.

### D8 — Capacity envelope

At p95 write rate (50 mutations/sec across all users on a single host), the ring holds ≤ 15 000 rows (5 min × 60 s × 50/s). With the composite `(Channel, ServerSeq)` index, replay reads stay under 5 ms. SQLite WAL handles this load without contention; no Redis, no message broker, no sidecar process.

## 3. Consequences

### Positive

- **Multi-worker reconnects now correct** — closes the silent-gap data-loss class flagged by AUDIT-06.
- **Zero new infra** — uses the same SQLite file as the rest of the plugin (or a separate `sse-ring.sqlite` if ADR-0005 split-DB applies; see §5).
- **Durable across worker restarts** — a `pkill php-fpm` no longer wipes the in-flight 5-minute window.
- **Backpressure-free** — readers don't block writers under WAL.
- **Inspectable** — operators can `SELECT … FROM SseRing` to debug live event flow.

### Negative

- Adds **one INSERT per mutation** to the action transaction — measured at ~0.2 ms on commodity SSD, well within the action's existing budget.
- Reaper is a fixed 60 s cadence — worst-case ring size is 6× expected, still bounded.
- SQLite `AUTOINCREMENT` adds the `sqlite_sequence` row — acceptable cost for monotonic `ServerSeq` (required by `Last-Event-ID` semantics).

### Neutral

- This ADR is **runtime-internal**: no public API or wire-format changes vs. ADR-0025. Frontend code is unchanged.
- The 5-minute window remains the spec invariant; only the **storage substrate** changes from per-process memory to shared WAL.

## 4. Compliance Gates

| Gate ID | Severity | Description |
|---|---|---|
| `G-27-RING-IS-SQLITE-WAL` | **CI** | The realtime DB connection MUST set `PRAGMA journal_mode = WAL` at boot. CI runs `PRAGMA journal_mode;` and asserts the result equals `wal`. |
| `G-27-PRODUCER-COMPLETENESS` | **CI** | Any REST handler mutating `Items`, `Mirrors`, `Favorites`, or `Trash` MUST `INSERT INTO SseRing` in the same transaction. Static analysis grep: every handler with a write SQL must have a matching `SseRing` insert; offenders fail PHPStan custom rule. |
| `G-27-NO-INPROCESS-PUBSUB` | **CI** | No PHP source file may reference `pcntl_fork`, `posix_kill`, `shared memory` (`shm_*`), or any in-process pub/sub library. `phpcs` deny-list. |
| `G-27-NO-EXTERNAL-BROKER` | **CI** | No `composer.json` dependency may pull Redis, Memcached, RabbitMQ, NATS, or Pusher clients. CI scans `composer.lock` against an explicit deny-list. |
| `G-27-RING-TTL-300S` | **TEST** | Reaper test inserts 1000 rows with `CreatedAtUnix - 301`, runs the cron, asserts `COUNT(*) = 0`. |
| `G-27-COLD-GAP-RESYNC` | **TEST** | Acceptance test: connect with `Last-Event-ID = 1`, but oldest ring row is `ServerSeq = 5000` → server MUST emit one `event: resync` frame and close. |
| `G-27-MULTIWORKER-REPLAY` | **TEST** | Integration test with 4 PHP-FPM workers: write 100 events, reconnect from each worker in turn, assert every reconnect sees all 100 in order. |
| `G-27-SERVERSEQ-MONOTONIC` | **DOC-NORM** | `ServerSeq` MUST be strictly monotonically increasing per host; gaps from rolled-back transactions are tolerated, reordering is not. |

## 5. Open Follow-Ups

1. **Split-DB placement** (ADR-0005) — decide whether `SseRing` lives in the main `workflowy.sqlite` or a dedicated `sse-ring.sqlite`. Default: dedicated file so reaper VACUUMs don't touch user data. Tracked separately.
2. **Cross-host scale-out** — if a deployment fronts >1 WordPress host behind a load balancer with sticky sessions disabled, this ADR is insufficient (each host has its own SQLite). At that scale, the project would need a re-evaluation of ADR-0002 (WordPress plugin only). Out of scope for v1.
3. **Compression** — `PayloadJson` could be `zstd`-compressed for very large mutations; deferred until profiling shows need.
